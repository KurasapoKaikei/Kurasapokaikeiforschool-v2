# A 群 — スキーマ確定に必須

## A-1 ★ 会計年度の開始月が実装内で矛盾しています

**現状の実装**

| 箇所 | 値 |
|------|-----|
| `src/lib/schoolCategoryUsage.ts:46-54` `getFiscalYearDateRange()` | **4/1 〜 翌 3/31 固定**（ハードコード） |
| `src/lib/schoolTheme.ts:18` `SCHOOL_FISCAL_PERIOD` | **`"2026.8.1～2027.7.31"`**（8 月始まり） |
| 学校登録フォーム（`src/app/register/school/page.tsx`） | 会計期間の入力欄が **ない** |

**何が起きているか**

ヘッダーには「2026.8.1〜2027.7.31」と表示されるのに、取引日の登録可否・集計の判定は `getFiscalYearDateRange()`（4/1〜3/31）で行われています。`resolveFiscalDateBounds()` は以下 7 箇所で使われており、**8 月始まりの学校では 4〜7 月の取引が「会計期間外」として登録できない**状態です。

```
src/app/club/accounting/register/new/page.tsx
src/app/club/accounting/register/csv/[id]/page.tsx
src/components/accounting/BankCsvImportSection.tsx
src/components/accounting/EditTransactionModal.tsx
src/components/accounting/NewTransactionModal.tsx
src/components/school/SchoolAuditPeriodView.tsx
src/lib/fiscalDateBounds.ts
```

**質問**

1. 会計年度は **全校 4 月始まり固定**ですか、それとも **学校ごとに可変**ですか
2. 可変の場合、**開始月のみ**（1〜12 月から選択）ですか、**任意の開始日**（例: 8/21）まで許容しますか
3. `SCHOOL_FISCAL_PERIOD` の「8.1〜7.31」は**デモ用の仮の値**ですか、それとも**実在の顧客の会計期間**ですか

**なぜ重要か**

Prisma の `FiscalYear` は `startDate` / `endDate` を持つので DB 側は可変に対応できます。しかし可変にするなら、学校マスタに会計期間の設定を追加し、`getFiscalYearDateRange()` を学校依存に書き換える必要があります。**固定か可変かでスキーマとアプリ改修の規模が変わります。**

**回答**:
1．学校ごとに可変です。
2．申し込み時に決算日を入力する欄がありますので、決算日をもとに会計期間を決定します。例えば決算日が8月20日だった場合、会計期間は8月21日～8月20日になります。
3．「8.1～7.31」は仮の値です。ですが、今見ながら確認している「クラサポ大学」のアカウントは4.1～3.31にしているので、8.1～7.31のアカウントがいつ作ったやつなのか分かりません。（何回か確認用のアカウントを作り直しています）

## A-4 金額を「円単位の整数」に変更してよいですか

**現状**

| 箇所 | 型 |
|------|-----|
| `src/utils/amountInput.ts:22-25` `isAllowedSignedIntegerTyping()` | 正規表現 `/^-?\d*$/` → **小数を受け付けない・負数は許容** |
| `prisma/schema.prisma` | `Decimal @db.Decimal(12,2)` |

**提案**

DB の型を **`Int`（円・負数許容）** に変更したいと考えています。理由は 3 点です。

1. 円に小数は存在せず、`(12,2)` という精度指定が実態と乖離している
2. Prisma の `Decimal` 型は JS の `number` と直接やり取りできず、集計のたびに変換が必要
3. 集計値が `Int` の上限（約 21 億円）を超える懸念は、SQL の `SUM(int)` が `bigint` に昇格するため問題ない

**質問**

1. **小数の金額を扱う場面は本当にありませんか**（外貨・按分・単価×数量など）
2. 負数（返金・取消の `△` 表記）を許容する理解で合っていますか
3. 1 取引で 21 億円を超えることはありませんか

**回答**:
1．ありません。
2．合っています。
3．ありません。

## C-2 日付は `YYYY-MM-DD` 文字列で扱い続けます

現行実装は取引日を `YYYY-MM-DD` の文字列で保持しています（`src/utils/dateDisplay.ts`）。DB 移行後もこの扱いを維持し、DB へは **UTC 深夜 0 時**の値として渡す方針です。

JST 環境で `new Date("2026-04-01")` は UTC の 2026-03-31T15:00 と解釈されるため、そのまま `date` 型に保存すると **2026-03-31 になり、会計年度をまたいで 1 日ずれます**。期首・期末付近の取引で必ず表面化するため、日付を Date オブジェクト経由で扱わないルールにします。

現行実装がすでに文字列ベースなので、**この方針は既存コードと相性が良い**と考えています。

**回答**:
文字列で相性が良ければ現行実装のままお願いします。

`normalizeNameForCompare()`（`src/utils/nameNormalize.ts`）は NFKC 正規化 + 小文字化 + trim を行っていますが、**DB のユニーク制約は正規化前の生文字列にかかります**。

そのため「消耗品費」と「消耗品費（全角スペース入り）」のような差は DB 制約では弾けません。**正規化した値を別カラムに持ってユニーク制約をかける**方式に変えたいと考えていますが、問題ありますか。

**回答**:
問題ないかと思います。
