# クラサポ会計 for school — インフラストラクチャ設計書

**文書バージョン**: 1.5.0
**作成日**: 2026-08-18
**位置づけ**: 現行のプロトタイプ（localStorage 正本）から、個人情報と金銭記録を扱う本番マルチテナント SaaS へ移行するための、基盤・データ・セキュリティ・運用の設計正本。
**前提選択**: ① 本番 SaaS 移行の全体設計 ／ ② クラウド基盤 = **AWS** ／ ③ データ移行 = **localStorage から PostgreSQL へ全面移行**
**コスト方針**: **スモールスタート。ランニング費用を最小限に抑える。** 月額 **約 1.8 万円**（年 約 21 万円）を目標とする。開発期間中（実データ投入前）は WAF / GuardDuty を無効にして **約 1.5 万円**に抑える。
**構成方針**: **本番・ステージングの 2 環境は最初から用意する**（デプロイ検証と顧客デモの経路を確保するため）。一方で **マルチ AZ 冗長化は当面行わない**（RDS は Single-AZ、アプリは 1 タスク）。削った項目とそれによるリスクは §6.6 に、事業成長に応じた増設順序は §6.7 に明記する。

> サーバーの具体値（ランタイム、サイジング、DB パラメータ、データ型、タイムアウト、アップロード上限、環境変数）は [`server-spec.md`](./server-spec.md) に分離しています。
>
> 本書はインフラおよびデータ永続化層の正本です。業務仕様は `docs/spec_latest.md`、全体設計は `docs/system-grand-spec.md` を参照してください。本書と業務仕様が矛盾する場合は、本書のインフラ記述を優先し、業務仕様側を追随修正します。

### 1.2 インフラ観点での決定的事実

1. **サーバー状態を持たない。** 永続化はすべてクライアント側。したがって現状の「インフラ要件」は事実上未定義であり、本設計はゼロベースの新規構築となる。
2. **Prisma スキーマは資産だが実接続は限定的。** 20 モデルが定義済みだが、実際に DB を触るのは `budgetDb.ts` / `parentScope.ts` / `collectionPayment.ts` / `collectionPaymentSync.ts` の 4 ファイルのみ。
3. **永続化アクセスが `src/lib` / `src/utils/localStorage.ts` に集約されている。** これは移行上の**最大の追い風**。ページ層が直接 `localStorage` を叩くのではなく、名前付き関数（`loadTransactions()` 等）を経由する設計になっているため、この層を差し替えれば移行できる。
4. **`prisma/migrations` が `.gitignore` されている。** マイグレーション履歴が存在せず、`db push` 運用。本番運用には致命的で、最優先の是正対象。

**ここはコスト削減の対象にしない。** 以下はインフラ構成の大小にかかわらず、実データ投入前に必ず解消する。

## 2. 設計目標と非機能要件

### 2.1 設計原則

1. **正本はサーバー（PostgreSQL）に置く。** ブラウザはキャッシュに徹する。
2. **テナント分離は多層防御。** アプリ層のフィルタだけに依存せず、DB の Row Level Security で backstop する。**これはソフトウェアで実現でき、費用はかからない。**
3. **会計データは追記的に扱う。** 物理削除ではなく論理削除＋監査ログ。
4. **既存 UI を壊さない。** `.cursor/rules` の方針どおり、画面・配色・レイアウトは維持し、差し替えるのは永続化層に限定する。
5. **Infrastructure as Code。** 手動でのコンソール操作を本番構成に残さない。
6. **費用は「無料または安価な手段で代替できるものは代替する」。** マネージドサービスの利便性より、月額の低さを優先する。ただし **①データ消失 ②個人情報漏洩 ③改ざん** の 3 つに直結する対策は削らない。

### 2.2 非機能要件（目標値）

最小構成で現実的に達成できる水準に設定する。過大な目標を掲げて実態と乖離させない。

| 項目 | 目標 | 備考 |
|------|------|------|
| 可用性 | **99.0%**（月間ダウンタイム 7.2 時間以内） | **冗長構成を持たないため、控えめに設定する。** 実測はこれより高くなる見込みだが、障害が 1 回起きれば下回りうる |
| 計画停止 | **月 1 回・10 分以内**を許容 | RDS のメンテナンスウィンドウ（深夜帯に設定）、インスタンスクラス変更 |
| RTO（リージョン内） | **1 時間** | RDS の自動復旧またはスナップショットからの復元 |
| RTO（リージョン障害） | **8 時間** | 大阪リージョンでスナップショットから再構築（IaC 適用 + リストア） |
| RPO | **5 分**（PITR） | RDS 自動バックアップの継続的アーカイブによる |
| レスポンス | 主要画面 p95 < **2.0 秒**、帳票集計 p95 < 4.0 秒 | `db.t4g.micro` のバースト特性を織り込んだ値 |
| 同時接続 | スモールスタート想定 **10〜20 学校 × 平均 15 クラブ = 150〜300 テナント**、ピーク同時 **50 セッション** | 50 校規模に達したら §6.7 の増設を実施 |
| 障害検知 | 5 分以内に検知しメール / Slack 通知 | 外部無料監視 + CloudWatch アラーム |
| データ保存期間 | 会計帳簿・証憑 **7 年** | 法人税法・学校法人会計基準に準ずる。**S3 の保管費用は安価なため削らない** |
| データ所在 | **日本国内のみ**（ap-northeast-1 主 / バックアップのみ ap-northeast-3） | 学校・大学の調達要件で国内保管を求められる想定 |

> **可用性目標を 99.0% に下げた理由**: RDS Single-AZ・アプリ 1 タスクという構成で 99.5% 以上を掲げると、実態と乖離する。数値を下げるのではなく、**冗長化を入れた時点で目標を上げる**（§6.7）という順序にする。顧客との契約に SLA を明記しない方針（§7 D-12）とも整合する。

### 3.2 コンピュート — ECS Fargate（パブリックサブネット配置）

| 候補 | 月額目安（prod） | 判定 |
|------|---------------|------|
| **ECS Fargate 1 タスク + ALB（パブリックサブネット）** | 約 $45 | **採用**。NAT 不要で最も安く、VPC 内の RDS へ直結できる |
| ECS Fargate（プライベートサブネット + NAT） | 約 $100 | 不採用。NAT Gateway だけで月 $55（¥8,250）増える |
| AWS App Runner | 約 $50 | 不採用。RDS 接続に VPC コネクタが要り、その場合 NAT が必要になって結局高くなる |
| API Gateway HTTP API + VPC Link（ALB を置かない） | 約 $24 | 不採用。ALB の $22 を削れるが、30 秒のタイムアウト上限が CSV 一括取込に影響し、構成も複雑になる |
| OpenNext + Lambda | 約 $20 | 不採用。最安だが Prisma のコールドスタートと VPC Lambda の遅延、構築の複雑さが見合わない |

**構成詳細**

| 項目 | 設計 |
|------|------|
| コンテナイメージ | **`node:20-slim`（Debian bookworm）** ベース、Next.js standalone 出力。alpine（musl）ではなく glibc 系を選ぶのは、Prisma のエンジンバイナリで環境差の事故が起きやすいため。`schema.prisma` の `binaryTargets` に `debian-openssl-3.0.x` を指定済み |
| タスクサイズ | **0.5 vCPU / 1 GB**（Next.js SSR の実用下限） |
| 常時タスク数 | **1**（AZ 冗長は当面行わない） |
| オートスケール | 1 〜 3。CPU 70% で追加。**決算期（3月・7月）のみ下限 2 にスケジュール変更** |
| ヘルスチェック | **`/api/health`（DB 疎通を見ない浅いチェック）**。ALB 猶予 60 秒。DB 込みの深いチェックは `/api/health/deep` に分離 |
| デプロイ | ローリング（`minimumHealthyPercent: 100` / `maximumPercent: 200`）。**1 タスクでも新タスク起動後に旧タスクを落とすため、デプロイ時の停止は発生しない** |
| 障害時 | タスク異常終了時は ECS が自動で再起動。**復帰まで 1〜2 分の停止が発生する**（2 タスク化すればゼロになる。§6.7 第 1 順位） |

**ヘルスチェックを 2 系統に分ける理由**

| エンドポイント | 用途 | DB 疎通 | 異常時 |
|--------------|------|--------|-------|
| `/api/health` | **ALB ターゲットグループ** | 見ない | — |
| `/api/health/deep` | 外形監視・CloudWatch アラート | 見る | 503 |

ALB のヘルスチェックで DB 疎通を判定すると、**DB が一時的に落ちた際に全タスクが unhealthy と判定されて ECS がタスクを落とし続け、DB 復旧後も再起動ループから抜けられなくなる**。1 タスク運用では特に致命的なため、ALB には浅いチェックのみを見せる。

**シングル AZ・1 タスク運用について**

ALB は仕様上 **2 つ以上の AZ のサブネット**を要求するため、VPC には 2 AZ 分のサブネットを作成する。ただし**サブネットを作ること自体に費用はかからない**ため、実際に稼働させる Fargate タスクと RDS は 1a に寄せ、実質シングル AZ で運用する。

これにより、将来 AZ 冗長化する際は**ネットワークを作り直す必要がなく、タスク数と RDS の Multi-AZ フラグを変えるだけ**で済む。`infra/config/*.env` の `ECS_DESIRED_COUNT` と `DB_MULTI_AZ` でパラメータ化してある（§3.10）。

**パブリックサブネット配置について**

NAT Gateway は本番だけで月 $55（¥8,250）かかり、最小構成では総額の 3 割を占めてしまう。Fargate タスクをパブリックサブネットに置き、パブリック IP を付与して IGW 経由で直接 egress させれば NAT は不要になる。

セキュリティは以下で担保する。

- タスクのセキュリティグループは **ALB のセキュリティグループからの inbound のみ許可**（インターネットからの直接到達は不可）
- **RDS はプライベートサブネットのまま**（インターネット経路なし・`publiclyAccessible: false`）
- ALB は CloudFront からのみ受け付ける（カスタムヘッダ検証 + マネージドプレフィックスリスト）

これは AWS が公式に示しているコスト削減パターンであり、実質的なリスク増は小さい。将来 NAT を追加してプライベート配置へ移す場合も、CDK のサブネット指定を変えるだけで済むよう構成する。

### 3.3 データベース — RDS PostgreSQL（Aurora ではなく）

| 項目 | 本番 | ステージング |
|------|------|------------|
| エンジン | **RDS PostgreSQL 16** | 同左 |
| インスタンス | **db.t4g.micro**（2 vCPU バースト / 1 GB） | db.t4g.micro（**平日日中のみ起動**） |
| ストレージ | gp3 20 GB（自動拡張上限 100 GB） | gp3 20 GB |
| 冗長化 | **Single-AZ** | Single-AZ |
| 暗号化 | KMS（AWS 管理キー・無料） | 同左 |
| バックアップ | 自動バックアップ **7 日** + PITR（DB サイズ以内は無料）。日次スナップショットを **AWS Backup で backup アカウント + 大阪へコピー** | 1 日 |
| 接続 | Prisma 直結（Fargate は長寿命タスクのためプール枯渇なし）。**RDS Proxy は使わない** | 同左 |
| 削除保護 | 有効 | 無効 |

**なぜ Aurora ではなく RDS `db.t4g.micro` か**

| 選択肢 | 月額 | 判断 |
|--------|------|------|
| Aurora Serverless v2（最小 0.5 ACU） | 約 $73 | 下限が高すぎる。スモールスタートには不釣り合い |
| RDS `db.t4g.small`（2 GB） | 約 $30 | 余裕はあるが、150〜300 テナント規模では過剰 |
| **RDS `db.t4g.micro`（1 GB）** | **約 $16** | **採用**。スモールスタートの規模に見合う。上位クラスへの変更はいつでも可能 |

**`db.t4g.micro` で運用するための前提**

- PostgreSQL のパラメータグループで `shared_buffers` / `work_mem` / `max_connections` を 1 GB 向けに調整する（デフォルトのままだとメモリ不足を起こしやすい）
- Prisma の接続プールを **`connection_limit=5` 程度に制限**する（Fargate 1 タスクなので十分）
- 重い帳票集計は SQL 側で集約し、アプリでのループ処理を避ける（§4.4）
- **バーストクレジット残高のアラームを必ず設定する**（§3.12）。クレジット枯渇時は性能が急落する

**トレードオフ（明示）**

- **Single-AZ のため、インスタンス障害時は復旧に 10〜30 分かかる**。Multi-AZ にすると月 $16 増になるが、**ユーザーの方針により当面は行わない**（§6.7 第 2 順位）
- 決算期のピークには**手動でインスタンスクラスを変更**する（`db.t4g.small` / `medium` へ。数分のダウンタイムを伴う計画メンテナンス）。3月・7月の前に実施する運用とする
- メンテナンスウィンドウ（月 1 回・数分）は**深夜帯（例: 日曜 03:00 JST）に設定**し、学校の業務時間を避ける

**1 年間の Reserved Instance（前払いなし）を適用すれば約 30% 引き**（$16 → $11）になる。構成を変えずに効くため、稼働が安定した時点で適用する。

### 3.4 オブジェクトストレージ — S3（証憑・帳票）

証憑の保管費用は 7 年分でも安価であり、**ここは削らない**。

| バケット | 用途 | 設定 |
|---------|------|------|
| `kurasapo-receipts-prod` | 証憑画像（レシート・通帳残高） | **SSE-S3**（KMS ではない。KMS はリクエストごとに課金されるため）/ バージョニング有効 / パブリックアクセス全ブロック |
| `kurasapo-exports-prod` | 決算書 PDF・CSV エクスポート | SSE-S3 / ライフサイクル 90 日で削除 |

**アクセス方式**

- アップロード: サーバーが発行する **署名付き URL（PUT、有効期限 5 分）** でブラウザから直接 S3 へ。Fargate のメモリ・帯域を消費しない（＝タスクサイズを小さく保てる）
- 閲覧: 署名付き URL（GET、有効期限 15 分）
- ライフサイクル: Standard → 90 日で Standard-IA → 1 年で Glacier Instant Retrieval

**Object Lock は当面見送る**。電子帳簿保存法が求める「訂正・削除の防止または履歴の保存」は、**バージョニング + アプリ側の AuditLog（§3.6）** で満たす方針とする。Object Lock 自体に追加料金はかからないが、Compliance モードは誤設定時に取り消せず、運用が固まる前に有効化するとリスクが大きい。**運用が安定した時点で有効化する**（§6.7）。

### 3.5 認証・認可

**ここはソフトウェアで実装するため、インフラ費用はかからない。** 最小構成でも一切妥協しない。

#### 3.5.1 認証基盤 — Auth.js v5（NextAuth）+ Prisma

Cognito ではなく Auth.js を選ぶ理由:

- 本システムのログイン識別子はメールアドレスではなく、**クラブ ID（学校が発行）**、**監査人 ID（`AUD-XXXX`）**、**学校 ID（`SCH-XXXXX`）** と、テナント固有の体系を持つ。Cognito のユーザープールにこれを載せると、テナント跨ぎの ID 衝突回避と属性設計が煩雑になる
- 同一人物が「作業者」「責任者」など複数ロールを持ち、ロールがテナント側マスタで管理される。認可情報の正本は自前 DB に置くのが自然
- **Cognito は MAU 課金**であり、学校数が増えるほど費用が増える。Auth.js は自前 DB で完結するため追加費用がない
- 学校側から **学認（GakuNin）SAML / Microsoft Entra ID との SSO** 要件が出た段階で、SAML プロバイダを追加する拡張余地を残す

| 項目 | 設計 |
|------|------|
| ライブラリ | Auth.js v5（Credentials Provider）+ Prisma Adapter |
| パスワードハッシュ | **argon2id**（メモリ 64MB / 反復 3 / 並列 4） |
| セッション | **DB セッション**（JWT ではない）。強制ログアウトと権限の即時反映を可能にするため |
| Cookie | `httpOnly` / `secure` / `SameSite=Lax` / セッション有効期限 8 時間・スライディング更新 |
| 多要素認証 | 学校管理者は **TOTP 必須**（`otplib` 利用・追加費用なし）、監査人は任意 |
| 初期パスワード | 学校が発行 → 初回ログイン時に**強制変更** |
| ログイン試行制限 | 同一 ID 5 回失敗で 15 分ロック（DB カウンタ） |
| 保護者 | 第 1 段階は `parentViewToken` の署名付き URL（閲覧専用・失効可能）。第 2 段階でメール OTP |

#### 3.5.2 認可 — テナント境界

| ロール | 参照範囲 | 更新範囲 |
|--------|---------|---------|
| 学校管理者 | 自校の全クラブ | 学校マスタ、共通カテゴリー/科目、監査期間、承認・ロック |
| クラブ責任者（manager） | 自クラブ | 部内承認、決算提出 |
| クラブ作業者（worker） | 自クラブ | 取引・集金・部員の入力編集 |
| 監査人 | 担当割当クラブのみ | 監査ステータス、メッセージ |
| 保護者 | 自児の集金レコードのみ | なし（閲覧専用） |

**実装は三層で担保する（いずれも追加費用なし）。**

1. **ミドルウェア層** — `src/middleware.ts` で URL プレフィックス（`/school` `/club` `/audit`）とセッションのロールを突合し、越境リクエストを 403 で遮断
2. **アプリケーション層** — Prisma Client Extension でクエリに `schoolId` / `clubId` を自動注入。開発者が `where` を書き忘れても漏れない
3. **データベース層** — PostgreSQL **Row Level Security**。リクエストごとにトランザクション内で `SET LOCAL app.current_school_id` を設定し、全テーブルにポリシーを適用

```sql
-- 全テナントテーブルに適用するポリシーの例
ALTER TABLE "Transaction" ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON "Transaction"
  USING ("schoolId" = current_setting('app.current_school_id', true));
```

### 3.6 監査証跡（AuditLog）

会計システムとして必須。**DB テーブル 1 つで実現でき、追加のインフラ費用はかからない。** 追記専用（UPDATE / DELETE をロールで禁止）とする。

| カラム | 内容 |
|--------|------|
| `actorId` / `actorRole` / `actorName` | 誰が |
| `at` | いつ（UTC） |
| `action` | CREATE / UPDATE / DELETE / APPROVE / REJECT / LOCK / LOGIN / EXPORT |
| `entityType` / `entityId` | 何を |
| `before` / `after`（JSONB） | どう変えたか |
| `schoolId` / `clubId` | どのテナントで |
| `ipAddress` / `userAgent` | どこから |

保存期間 7 年。RDS のストレージ費用は gp3 で $0.138/GB のため、7 年分でも数ドル規模に収まる。1 年経過分を S3（JSON Lines）へ退避する処理は、**ストレージが 50 GB を超えた時点**で実装する。

### 3.9 環境分離

**本番とステージングの 2 環境は最初から用意する。** ここは費用を理由に削らない。デプロイとマイグレーションを本番でぶっつけ本番にすると、会計データの破損という取り返しのつかない事故につながるため。

| 環境 | AWS アカウント | 用途 | 構成 | 月額 |
|------|--------------|------|------|------|
| **dev** | なし（**ローカル**） | 日常の開発 | Docker Compose（Next.js + PostgreSQL 16 コンテナ） | **0 円** |
| **staging** | prod と同一アカウント（**同一 VPC・別サブネットグループ**） | デプロイ検証・マイグレーション検証・受入テスト・顧客デモ | Fargate 1 タスク + RDS `db.t4g.micro`。**ALB は本番と共有**（ホストベースルーティング）。**平日日中のみ起動** | 約 2,700 円 |
| **prod** | 専用アカウント | 本番 | 本設計のフル構成 | 約 14,100 円 |
| backup | 専用アカウント | バックアップ隔離先 | **AWS Backup ボールトのみ**（常時稼働リソースなし） | 約 450 円（prod 側に計上） |

**staging を「平日日中のみ起動」にする理由**: staging の役割はデプロイ検証と顧客デモであり、24 時間動かす必要がない。EventBridge スケジュールで平日 08:00 起動 / 20:00 停止（Fargate は desiredCount 0、RDS は停止）とすることで、費用が約 6 割減る。**顧客デモの予定がある日は手動で起動**する運用とし、その手順を Runbook に残す。

> **注意**: RDS の停止は **7 日で自動的に再起動**される仕様のため、週次で再停止するスケジュールも併せて設定する。

**dev をローカルに寄せる理由**: クラウド上の開発環境は、使っていない時間も NAT・RDS・ALB の費用が発生する。Docker Compose で PostgreSQL を立てれば、Prisma のマイグレーションもシードも同じように検証でき、費用はゼロになる。**最小構成における最大の節約ポイントの一つ。**

**staging を本番と同一アカウント・同一 VPC・ALB 共有にする理由**: アカウントや VPC を分けると ALB がもう 1 台必要になり、それだけで月 $22（¥3,300）増える。ホストベースルーティング（`staging.kurasapo.jp`）で 1 台の ALB を共有すれば、追加費用はリスナールール分のみで済む。

**分離は以下で担保する**（同一 VPC 内でも実質的な分離は成立する）。

- **RDS インスタンスは prod / staging で別**にする。同一インスタンス内の別データベースで済ませることは**しない** — staging の負荷や誤操作が本番の会計データに影響する経路を作らないため
- セキュリティグループを環境ごとに分け、**staging のタスクから prod の RDS へ到達できないようにする**
- IAM ロール・Parameter Store のパスも環境ごとに分離（`/kurasapo/prod/*` と `/kurasapo/staging/*`）
- staging には**本物の個人情報を置かない**（匿名化データのみ）

**backup アカウントだけは分ける。** これは費用ではなく**リスクの問題**。本番アカウントの認証情報が侵害された場合でも、バックアップまで同時に破壊されない状態を作る。AWS Organizations の追加アカウントは無料であり、費用は保管しているスナップショット分（月 $5 程度）のみ。**バックアップと本番が同一アカウントにある構成は、バックアップが無いのと同じリスクを抱える。ここは削らない。**

### 3.10 IaC — AWS CLI スクリプト（`infra/`）

構築手段は **AWS CLI のシェルスクリプト**とする（実装済み。手順は `infra/README.md`）。

```text
infra/
├── README.md                 # 構築手順・トラブルシュート
├── config/
│   ├── common.env            # 全環境共通（リージョン / VPC CIDR / ドメイン / アカウントガード）
│   ├── prod.env              # 本番のサイズ設定
│   └── staging.env           # ステージングのサイズ設定
├── lib/common.sh             # 冪等ヘルパー・検索関数・Windows パス変換対策
├── 00-preflight.sh           # 前提チェック（何も作らない）
├── 10-network.sh             # VPC / IGW / サブネット x4 / ルートテーブル / S3 EP / SG x3
├── 20-data.sh                # DB サブネットグループ / RDS / S3 x2 / SSM シークレット
├── 30-registry.sh            # ECR + ライフサイクルポリシー
├── 40-compute.sh             # IAM x2 / ロググループ / ECS / ALB / TG / リスナー / サービス
├── 50-observability.sh       # SNS / CloudWatch アラーム x8 / コスト異常検知
├── deploy.sh                 # ビルド → push → マイグレーション → サービス更新
└── 99-teardown.sh            # 逆順削除（S3 と最終スナップショットは既定で残す）
```

**設計上の約束**

| 項目 | 方針 |
|------|------|
| 冪等性 | 全リソースを「検索してから作る」。同じスクリプトを何度実行しても結果は同じ |
| 状態管理 | 作成したリソース ID を **SSM Parameter Store** に保存。ローカル state ファイルを持たないため、複数人・複数マシンから同じ手順を再現できる |
| 事故防止 | **`AWS_PROFILE_NAME` と `EXPECTED_ACCOUNT_ID` を両方必須にし、どちらか欠ければ何も作らず停止する**。AWS CLI はプロファイル未指定時に `~/.aws/credentials` の `[default]` へフォールバックするため、開発機に複数プロジェクトのプロファイルがあると指定漏れがそのまま別アカウントの操作事故になる。暗黙のフォールバックを封じるための必須化であり、実アカウントと不一致ならリソースを 1 つも作らずに中断する |
| 環境の切替 | 全スクリプトが第 1 引数に `prod` / `staging` を取る。共有リソース（VPC / ALB / ECS クラスタ / ECR）は 2 回目の実行で自動的にスキップされる |
| Windows 対応 | Git Bash の MSYS パス変換（`/kurasapo/prod/...` が Windows パスに化ける）を `lib/common.sh` で無効化済み |
| 増設のしやすさ | AZ 冗長化は `config/*.env` の `ECS_DESIRED_COUNT` と `DB_MULTI_AZ` の変更で切り替わる（§6.7） |

**CloudFormation / CDK ではなく CLI を選ぶことのトレードオフ**

CLI 直叩きには「宣言的な差分適用がない」「コンソールでの手動変更によるドリフトを検知できない」「部分的な失敗からの復旧が弱い」という弱点がある。本スクリプト群は *検索してから作る* 形で冪等性を確保しているが、CloudFormation ほど堅牢ではない。

**運用が固まり変更が頻繁になった段階で CloudFormation / CDK への移行を検討する。** その際に `import` できるよう、リソース名とタグ体系（`Project` / `Env` / `ManagedBy=infra-cli`）は統一してある。

### 3.11 CI/CD — GitHub Actions

| トリガ | ジョブ |
|--------|-------|
| Pull Request | `npm ci` → ESLint → `tsc --noEmit` → `prisma validate` → `prisma migrate diff`（破壊的変更の検知）→ ユニットテスト → `next build` |

AWS 認証は **GitHub OIDC → IAM ロール**（長期アクセスキーを GitHub に置かない）。プライベートリポジトリの GitHub Actions 無料枠（月 2,000 分）で足りる想定。

**ECR のライフサイクルポリシー**を設定し、直近 10 イメージのみ保持する（放置すると ECR のストレージ費用が増え続けるため）。

> **最優先の是正**: `.gitignore` の `/prisma/migrations` を**削除**し、マイグレーション履歴を Git 管理下に置く。`db push` 運用は本番では使わない。

### 3.12 監視・可観測性（最小限）

「有料の高機能サービスを入れる」のではなく、「無料枠と CloudWatch の基本機能で必要十分をつくる」方針とする。

| レイヤ | 手段 | 費用 |
|--------|------|------|
| ログ | CloudWatch Logs（**構造化 JSON**、`requestId` / `schoolId` / `clubId` / `userId` を付与）。**保持 14 日**（それ以上は S3 へ手動退避） | 約 $2 |
| メトリクス | ECS / ALB / RDS の標準メトリクス（無料）。**Container Insights は使わない**（追加課金のため） | $0 |
| アラーム | CloudWatch Alarm 10 個 → SNS → メール / Slack | 約 $1 |
| エラー追跡 | **Sentry 無料枠**（月 5,000 エラー）。個人情報のスクラビング設定は必須 | $0 |
| 外形監視 | **UptimeRobot 無料枠**（5 分間隔・50 モニタ）で主要 3 URL を監視。CloudWatch Synthetics は 1 カナリアで月 $10 かかるため使わない | $0 |
| 分散トレーシング | **なし**。必要になったら X-Ray を追加（§6.7） | $0 |
| オンコール | SNS → メール + Slack。**PagerDuty は使わない** | $0 |

**主要アラーム**

| アラーム | 閾値 |
|---------|------|
| ALB 5xx 率 | 5 分平均 1% 超 |
| ALB p95 レイテンシ | 3 秒超が 5 分継続 |
| ECS 実行タスク数 | 期待数を下回る状態が 5 分継続 |
| RDS CPU | 80% が 10 分継続 |
| **RDS バーストクレジット残高** | 20% 未満（`db.t4g.micro` はバースト型のため必須） |
| **RDS 空きメモリ（FreeableMemory）** | 100 MB 未満（1 GB インスタンスのため必須） |
| **ECS タスク再起動の発生** | 即時（1 タスク運用のため、再起動＝サービス断） |
| RDS 空きストレージ | 20% 未満 |
| ログイン失敗数 | 5 分で 50 件超（総当たり検知） |
| バックアップジョブ失敗 | 即時 |
| GuardDuty の High/Critical 検出 | 即時 |
| 月間コストの異常増 | 予算比 130%（Cost Anomaly Detection・**無料**） |

> `db.t4g.micro` はバースト型インスタンスであり、CPU クレジットを使い切ると性能が急落する。またメモリが 1 GB しかないため、`FreeableMemory` の枯渇は接続断に直結する。**この 2 つのアラームは、スモールスタート構成では特に重要。**

### 3.13 バックアップ・災害対策

| 対象 | 方式 | 保持 | 復旧目標 |
|------|------|------|---------|
| RDS（日常） | 自動バックアップ + PITR（**DB サイズ以内は無料**） | 7 日 | RTO 1 時間 / RPO 5 分 |
| RDS（論理破壊・ランサム対策） | AWS Backup で **backup アカウント + 大阪リージョン**へ日次コピー（Vault Lock） | 35 日 | RTO 4 時間 |
| RDS（リージョン障害） | 上記スナップショットから大阪で再構築（CDK 適用 + リストア） | — | RTO 8 時間 |
| S3 証憑 | バージョニング + backup アカウントへ日次コピー | 7 年 | RPO 24 時間 |
| IaC / アプリコード | GitHub + ECR イメージ（直近 10 世代） | — | 即時 |

**多層バックアップの意図**: 「インスタンス障害」「リージョン障害」「論理破壊・誤操作・ランサムウェア」は別の障害であり、対策も別に要る。自動バックアップは 3 番目に効かない（同一アカウント内で削除できてしまう）。**アカウントを跨いだ Vault Lock 付きコピーだけが、認証情報の侵害に耐える。ここは月 $5 で買える保険であり、削らない。**

**復旧演習を半期に 1 回実施**する。手順書（Runbook）は `docs/runbook/` に整備し、**演習の実測 RTO を記録**する。演習していない DR は存在しないものと同じ。演習対象:

1. RDS の PITR による特定時刻への巻き戻し
2. backup アカウントからの完全リストア（本番アカウントが使えない前提）
3. 証憑バケットの誤削除からのバージョン復元

### 3.14 セキュリティ運用（最小限）

学生・保護者の個人情報と金銭記録を扱う以上、**無料または安価な範囲での検知・監査は必須**とする。

| サービス | 目的 | 費用 |
|---------|------|------|
| **CloudTrail（管理イベント）** | 全 API 操作の記録 | **無料**（90 日の証跡は標準で保持） |
| **GuardDuty** | 脅威検知 | 約 $10。**開発期間中は無効、実データ投入と同時に有効化**する。有料セキュリティサービスとして唯一残すもの |
| **S3 Block Public Access（アカウント全体）** | 誤公開の防止 | 無料 |
| **IAM Access Analyzer** | 過剰権限・外部共有の検出 | 無料 |
| **Cost Anomaly Detection** | 異常課金の検知（攻撃・暴走の兆候） | 無料 |
| **Dependabot / `npm audit`** | 依存パッケージの脆弱性 | 無料（GitHub） |
| **`trivy` によるイメージスキャン** | コンテナ脆弱性。GitHub Actions 内で実行 | 無料（Inspector の代替） |

**見送るもの**: Security Hub、AWS Config、Amazon Macie、Amazon Inspector、WAF Bot Control。合計で月 $200 超になるため、事業規模が拡大するまで導入しない（§6.7）。

**外部脆弱性診断**は、本番稼働前に **1 回のみ**実施する（想定 100〜150 万円）。年次実施は学校側から要求された時点で開始する。

### 3.15 法令・コンプライアンス

| 要件 | 対応 | 費用 |

## 4. データ移行設計（localStorage → PostgreSQL）

### 4.1 移行方針

方針は **全面移行**。ただし「一気に」の意味を、リリースを一度きりにするという意味ではなく、**二重管理期間を設けない**という意味で設計する。リポジトリ層を新設して内部実装を差し替え、テナント単位でカットオーバーする。

```text
【現在】  ページ (85本)  →  src/lib/*.ts / utils/localStorage.ts  →  localStorage
                                        ↑ ここを差し替える
【移行後】ページ (85本)  →  src/lib/*.ts（同名・async化）  →  API Route  →  Prisma  →  RDS
```

永続化アクセスが `src/lib` に集約されている現構造がそのまま移行の足場になる。ページ側の変更は**同期呼び出しの非同期化**に限定し、UI・レイアウト・配色には手を入れない（`.cursor/rules` 第 4 項の遵守）。

### 4.2 Prisma スキーマのギャップ

既存 `prisma/schema.prisma` は 20 モデルを持つが、現行 localStorage の実体をすべては表現できていない。以下を追加・修正する。

**追加が必要なモデル**

|-----------|---------------------|------|

| `Credential` | `schoolClubs.password` / `managerPassword` 等 | argon2id ハッシュ、初期 PW 強制変更フラグ、失敗回数 |
| `Session` | `kurasaokaikei-current-*` | Auth.js DB セッション |

| `ClubGroup` / `ClubGroupMember` | `kurasaokaikei-school-club-groups` | |

### 4.3 既存データの引き継ぎ

> **【2026-08-19 更新】アプリ担当者への確認により、実データを入れて運用・試用している学校は 0 校**（`docs/open-questions.md` A-3）。端末の入れ替え予定もない。
> したがって **本節のエクスポート / インポート導線は、本番リリース時点では不要**。P6（移行実施）はほぼ空になる。
> 以下は「リリース前に試用校が発生した場合」および「将来 localStorage 版から移ってくる顧客が出た場合」に備えた設計として残す。

**もし運用中の学校があれば、これは見落とすと致命的な論点になる。** データは**その担当者のブラウザにしか存在せず**、サーバー側にコピーが無いためである。

移行導線として以下を実装する。

1. **エクスポート画面**（`/school/settings/migration`）— ログイン中ブラウザの全 `classapo_*` / `kurasaokaikei-*` キーを 1 つの JSON にまとめてダウンロード
2. **インポート API**（`POST /api/migration/import`）— JSON を受け取り、(a) スキーマ検証（Zod）、(b) **ドライラン**で差分レポートを返す、(c) 承認後に冪等な取り込みを実行
3. **検証レポート** — 取り込み前後で「取引件数」「収入合計」「支出合計」「期末残高」をクラブ別に突合。**1 円でも合わなければ取り込みを中止**する
4. **カットオーバー** — 学校単位で実施。移行完了フラグを立てた学校のブラウザでは localStorage 書き込みを停止し、以降はサーバー正本のみ

移行前に、対象となる学校の担当者へ「移行日まではブラウザデータを消さない（Clear site data を実行しない）」ことを必ず周知する。

### 4.4 リポジトリ層の設計

```text
src/
├── repositories/          ← 新設。Prisma への唯一の入口
│   ├── transaction.repository.ts
│   ├── club.repository.ts
│   └── ...
├── app/api/               ← Route Handler（認証・認可・バリデーション・監査ログ）
│   ├── clubs/[clubId]/transactions/route.ts
│   └── ...
├── lib/                   ← 既存。関数シグネチャを維持したまま fetch 呼び出しへ差し替え
└── utils/localStorage.ts  ← 移行完了後に削除。移行期間中はキャッシュ層としてのみ残す
```

クライアント側のデータ取得は **TanStack Query** を導入し、現行の「`useEffect` で同期読み込み + `window` イベントで再描画」というパターンを、`useQuery` + `invalidateQueries` に置き換える。現行の 14 種の `*-changed` イベントは、そのままクエリキーの無効化にマッピングできる。

**ElastiCache を持たない構成のため、集計結果のキャッシュは以下で代替する。**

- サーバー側: Next.js の `unstable_cache` / `revalidateTag`（Fargate タスクのメモリ内。タスク間で共有されないが、データ整合性は各リクエストで DB を見るため崩れない）
- クライアント側: TanStack Query の `staleTime` を帳票系で長めに設定
- 重い集計（収支報告書・前年度比）は **DB のマテリアライズドビューまたは集計テーブル**で対応し、アプリ側でループしない

### 4.5 移行のフェーズ順序

| 順 | 対象 | 理由 |
|----|------|------|
| 1 | 認証・セッション・学校マスタ・クラブ一覧・監査人 | 他のすべてのデータのテナント境界を規定するため最初に確定させる |
| 2 | 共通カテゴリー・勘定科目・会計年度 | 取引データが参照する外部キーの供給元 |
| 3 | 部員・保護者 | 集金が参照する |
| 4 | 取引・繰延・証憑（S3 連携含む） | 最大ボリューム。ここで S3 アップロード導線を実装 |
| 5 | 集金予定・集金実績・入金履歴 | 取引と相互参照する |
| 6 | 予算・月次メモ・報告書備考・CSV 取込履歴 | 参照専用に近く影響が小さい |
| 7 | メッセージ BOX・決算ステータス・監査期間 | ワークフロー系。最後に移す |

| **Security Hub / Config / Macie / Inspector** | 30,000 円 | 構成ドリフト・個人情報の意図しない混入を**自動検知できない**。四半期ごとの手動レビューで代替 |

| **CloudWatch Synthetics** | 1,500 円 | 外形監視は UptimeRobot 無料枠（5 分間隔・死活監視のみ）。ログイン後の導線は監視できない |

| **AWS Business Support** | 53,100 円 | 本番障害時に **AWS へ技術的なエスカレーションができない** |
| **クラウド dev 環境** | 30,750 円 | 開発者はローカル Docker で作業。クラウド固有の問題は staging でしか踏めない |

**特に注意が必要な 3 点**

1. **1 タスク運用のため、タスクの異常終了がそのままサービス断になる。** ECS の自動復旧まで 1〜2 分。§3.12 の「ECS タスク再起動の発生」アラームで必ず検知できるようにする
2. **AWS Business Support がない状態で、可用性の数値を顧客に約束することは避ける。** 障害の原因が AWS 側にある場合、問い合わせる手段がない（§7 D-12）
3. **オンコール体制がない。** 決算期（3月・7月）だけは、当番制で Slack を監視する運用ルールを設ける

### 6.7 増設の順序（事業成長に応じて）

安いまま据え置くのではなく、**次の条件を満たした時点で順に足していく**。CDK のパラメータ変更で実施できるよう §3.10 で設計してある。

| 0 | **WAF + GuardDuty 有効化** | **実データを投入する日**（必須・交渉の余地なし） | +2,850 円 |
| 1 | **Fargate 2 タスク化** | **実データを持つ学校が 1 校でも稼働した時点**。AZ 冗長より先にこちら（プロセス障害の方が頻度が高い） | +3,450 円 |

**順序 0 と 1 だけは早い。** 実データが 1 件でも入った瞬間に、事故のコストが月数千円を大きく上回るため。
