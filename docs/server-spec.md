## 2. ランタイム仕様

### 2.1 アプリケーション

| 項目 | 値 | 備考 |
|------|-----|------|
| Node.js | **20.x LTS** | コンテナは `node:20-slim`（Debian bookworm） |
| Next.js | 14.0.4 | App Router / `output: 'standalone'` |
| 起動コマンド | `node server.js` | standalone の生成物 |
| 待受 | `0.0.0.0:3000` | `HOSTNAME` / `PORT` 環境変数 |
| 実行ユーザー | `nextjs` (uid 1001, gid 1001) | 非 root |
| TypeScript target | ES2017 | `tsconfig.json` |

**なぜ alpine ではなく slim か**: Prisma のクエリエンジンは musl 用と glibc 用でバイナリが分かれており、alpine では `binaryTargets` の指定漏れや OpenSSL バージョン差で起動時に落ちる事故が起きやすい。イメージサイズは 50MB ほど増えるが、glibc 系を選ぶ。`prisma/schema.prisma` の `binaryTargets` に `debian-openssl-3.0.x` を指定済み。

### 2.2 タイムゾーンとロケール

**方針: サーバーは一貫して UTC。JST への変換は表示層のみ。**

| レイヤ | 設定 | 根拠 |
|--------|------|------|
| コンテナ | `TZ=UTC` | タスク定義で明示 |
| PostgreSQL | `timezone=UTC` | パラメータグループで明示 |
| ブラウザ表示 | JST | `toLocaleString("ja-JP")` 等 |

**日付（取引日・納付期限）の扱い — 最重要**

会計上の日付は「暦日」であって時刻ではない。現行実装は `YYYY-MM-DD` の文字列で保持しており（`src/utils/dateDisplay.ts`）、この扱いを DB 移行後も維持する。

| ルール | 内容 |
|--------|------|
| DB 型 | `@db.Date`（時刻を持たない） |
| アプリ内表現 | **`YYYY-MM-DD` 文字列** |
| DB へ渡すとき | `new Date("YYYY-MM-DDT00:00:00.000Z")`（**必ず UTC 深夜 0 時**） |
| DB から読むとき | `date.toISOString().slice(0, 10)` |
| **禁止** | `getFullYear()` / `getMonth()` / `getDate()` をそのまま日付境界の判定に使うこと |

> **なぜ禁止か**: JST 環境で `new Date("2026-04-01")` は UTC 2026-03-31T15:00 として解釈される。これを `@db.Date` に渡すと **2026-03-31 として保存され、会計年度をまたいで 1 日ずれる**。期首（4/1）・期末（3/31）付近の取引で必ず表面化し、決算が合わなくなる。会計システムとして致命的な事故になるため、日付は文字列で扱い切る。

**日時（作成日時・更新日時）の扱い**

すべての日時カラムに **`@db.Timestamptz(3)`** を明示する。Prisma の `DateTime` は既定で `timestamp without time zone` にマップされるため、明示しないとタイムゾーン情報が落ちる。

### 2.3 文字コードと照合順序

| 項目 | 値 |
|------|-----|
| DB エンコーディング | **UTF8** |
| DB ロケール | **`en_US.UTF-8`** |

**ロケールを `en_US.UTF-8` にする理由**: RDS PostgreSQL のテンプレートデータベースは `en_US.UTF-8` 固定で、作成時にも変更できない。したがって選択の余地はない。**ローカル開発の `docker-compose.yml` もこれに合わせる**（`postgres:16` の Debian 版 + `--locale=en_US.UTF-8`）。ここを `C` にすると `ORDER BY name` の結果が開発と本番で食い違い、帳票の並び順が環境によって変わる。

**日本語の並び順を DB に期待しない。** 部員一覧の五十音順などは、アプリ側でカナ列を持って制御する（現行実装も `order` フィールドや `createdAt` で明示的に並べており、DB の照合順序に依存していない）。libc/ICU の日本語照合は環境差が大きく、RDS のマイナーバージョン更新で挙動が変わりうるため、会計帳票の並び順をそこに委ねない。

**名称の重複判定**は `normalizeNameForCompare()`（NFKC 正規化 + 小文字化 + trim、`src/utils/nameNormalize.ts`）をアプリ側で適用する。DB のユニーク制約は正規化前の生文字列にかかるため、**制約だけでは全角・半角の差を吸収できない**点に注意。

## 3. リソース仕様（サイジング）

### 3.1 アプリケーション（ECS Fargate）

| 項目 | prod | staging |
|------|------|---------|
| CPU | 512（0.5 vCPU） | 512 |
| メモリ | 1024 MB | 1024 MB |
| タスク数 | 1（AZ 冗長なし） | 1（平日日中のみ） |
| オートスケール | 1〜3（CPU 70%） | 0〜2 |

**メモリ配分（1024 MB の内訳）**

| 用途 | 目安 |
|------|------|
| Node.js ヒープ上限（`--max-old-space-size=640`） | 640 MB |
| Node ランタイム・Prisma エンジン・バッファ等 | 約 250 MB |
| OS・予備 | 約 130 MB |

Next.js の SSR プロセスは実測で 150〜300 MB に収まることが多く、640 MB のヒープ上限は十分な余裕がある。**上限を明示する理由**は、指定しないと Node がコンテナのメモリ制限を正しく認識できず、OOM Killer にタスクごと殺されることがあるため。ヒープ上限に当たれば少なくとも `heap out of memory` としてログに残る。

**CPU バーストの注意**: 0.5 vCPU は常時 0.5 コア相当であってバースト型ではない。Next.js のビルド済み SSR であれば十分だが、**CSV 一括取込や年間集計のような CPU 集約処理は同一プロセスを占有する**。重い集計は SQL 側に寄せる（§5.3）。

### 3.2 データベース（RDS PostgreSQL）

| 項目 | prod | staging |
|------|------|---------|
| エンジン | PostgreSQL 16 | 同左 |
| インスタンス | db.t4g.micro（2 vCPU バースト / 1 GB） | 同左 |
| ストレージ | gp3 20 GB（上限 100 GB まで自動拡張） | gp3 20 GB（上限 50 GB） |
| Multi-AZ | なし | なし |
| バックアップ保持 | 7 日 + PITR | 1 日 |

**メモリ配分（RDS の既定式に従う。明示固定はしない）**

| パラメータ | 既定式 | 1 GB での実値 |
|-----------|--------|--------------|
| `shared_buffers` | `{DBInstanceClassMemory/32768}` | 約 256 MB（25%） |
| `effective_cache_size` | `{DBInstanceClassMemory/16384}` | 約 512 MB（50%） |
| `max_connections` | `LEAST({DBInstanceClassMemory/9531392},5000)` | **約 112** |

メモリ系を固定値で上書きしないのは、**インスタンスクラスを上げたときに自動で追随させる**ため（決算期の一時的な `db.t4g.small` 化を想定。設計書 §3.3）。

**バースト型であることの帰結**: `db.t4g.micro` は CPU クレジットを消費して動く。クレジットが尽きるとベースライン（vCPU の 10%）まで性能が落ち、体感で「急に重くなる」。`CPUCreditBalance` のアラーム（閾値 30）は必須で、これが月に複数回発報するようならインスタンスクラスを上げる（設計書 §6.7 順序 2）。

### 3.3 接続数の設計

| 項目 | 値 | 算出 |
|------|-----|------|
| RDS `max_connections` | 約 112 | 上表 |
| アプリ 1 タスクあたり | **5**（`connection_limit=5`） | 接続文字列で明示 |
| 通常時の使用数 | 5〜15 | タスク 1〜3 |
| マイグレーションタスク | +5（一時的） | ワンショット実行時のみ |
| **ピーク見込み** | **約 20** | 上限の 18% |

RDS Proxy は使わない（設計書 §6.6）。Fargate タスクが長寿命なため Prisma のプールで足りる。**`connection_limit` を明示する理由**は、Prisma の既定値が `物理CPU数 × 2 + 1` で、Fargate の CPU 認識次第で想定外に増えるため。

`idle_in_transaction_session_timeout = 60000`（60 秒）を設定し、トランザクションを掴んだまま放置された接続を自動で切る。**接続リークが 1 タスク運用で起きると、DB 側の接続枯渇より先にアプリが応答不能になる**ため、安全弁として必須。

## 4. PostgreSQL パラメータ

`infra/20-data.sh` がパラメータグループ `kurasapo-postgres16` を作成し、インスタンス作成時に紐づける。

| パラメータ | 値 | 目的 |
|-----------|-----|------|
| `timezone` | `UTC` | §2.2 の方針を DB 側でも固定 |
| `log_min_duration_statement` | `1000`（ms） | 1 秒超のクエリをログに記録。遅延の切り分けに必須 |
| `log_statement` | `ddl` | マイグレーションによるスキーマ変更を追跡 |
| `idle_in_transaction_session_timeout` | `60000`（ms） | 接続リークの安全弁 |
| `work_mem` | `8192`（KB = 8 MB） | 帳票集計のソート・ハッシュ用 |
| `rds.force_ssl` | `1` | 非 SSL 接続を拒否（要再起動の静的パラメータ） |

### 4.3 `statement_timeout` を全体設定しない理由

暴走クエリ対策として `statement_timeout` は有効だが、**インスタンス全体に設定するとマイグレーションを巻き込む**。テーブルが大きくなった後の `ALTER TABLE` やインデックス作成は数分かかることがあり、これが途中で切られると中途半端な状態が残る。

したがって **アプリ用ロールにのみ設定する**。

```sql
-- アプリが使うロールにのみ 30 秒の上限をかける
ALTER ROLE kurasapo_app SET statement_timeout = '30s';
-- マイグレーション実行者（マスターユーザー）には設定しない
```

> **未実装**: 現状はマスターユーザーで接続している。P1（認証・認可）でアプリ専用ロールを作り、上記を適用する。あわせて RLS（設計書 §3.5.2）の適用先もこのロールになる。

## 5. データ仕様

### 5.1 金額

**円単位の整数。負数を許容する。**

現行実装（`src/utils/amountInput.ts`）は `/^-?\d*$/` で入力を検証しており、**小数を受け付けない**。一方で返金・取消のために **負数を許容**し、表示は `△` を使う。

| 項目 | 決定 |
|------|------|
| DB 型 | **`Int`**（円） |
| 範囲 | −2,147,483,648 〜 2,147,483,647（約 ±21 億円） |
| 負数 | **許容**（返金・取消） |
| 小数 | 使わない |

> **現行スキーマの誤り**: `prisma/schema.prisma` は `Decimal @db.Decimal(12,2)` を使っているが、これは本アプリに合わない。理由は 3 つ。①円に小数は存在しない ②Prisma の `Decimal` 型は JS の `number` と直接やり取りできず、集計のたびに変換が要る ③精度指定が実態（整数）と乖離しており、誤解のもとになる。**P2（スキーマ確定）で `Int` に変更する。**
>
> 集計値が 21 億円を超える懸念については、SQL の `SUM(int)` は `bigint` に昇格するため問題ない。1 レコードが 21 億円を超えることは実務上ない。

### 5.2 日付・日時

| 用途 | Prisma 型 | 備考 |
|------|----------|------|
| 取引日・納付期限・期首/期末 | `DateTime @db.Date` | §2.2 のルールを厳守 |
| 作成日時・更新日時・承認日時 | `DateTime @db.Timestamptz(3)` | ミリ秒精度・タイムゾーン付き |

### 5.3 集計の方針

収支報告書・予実管理・前年度比は、**アプリ側でループせず SQL の集約に寄せる**。

理由は 3 つ。①0.5 vCPU では数千行のループが体感できる遅延になる ②Fargate タスクのメモリ上限に近づく ③タスク間でキャッシュを共有しないため、アプリ側キャッシュの効果が薄い（ElastiCache を持たない構成のため。設計書 §6.6）。

| 対象 | 方針 |
|------|------|
| 月次・年次の科目別集計 | `GROUP BY` で SQL 集約。`(schoolId, clubId, fiscalYearId, categoryId, accountTitleId, date)` の複合インデックスを張る |
| 収支報告書 | 同上。必要なら集計テーブルまたはマテリアライズドビュー |
| 一覧のページング | **必ず `LIMIT` を付ける**。全件取得してアプリで切らない |

### 5.4 現行スキーマに不足しているフィールド

設計書 §4.2 のモデル追加に加え、**`Transaction` 単体でも localStorage 側にあって Prisma に無いフィールドが多数ある**。P2 で必ず補うこと。

| フィールド | 用途 |
|-----------|------|
| `transferGroupId` | 振替の対（出金 + 入金の 2 行）を束ねる |
| `deferredPlSide` / `deferredPlCategory` / `deferredPlSubject` | 繰延計上の収支紐付け（科目別台帳・収支集計） |
| `deferredRecordId` | 精算が対象とする計上仕訳 |
| `deferredSettlementMode` | 預り金の精算区分（`period` / `refund`） |
| `csvImportId` / `originalFileName` | CSV 一括取込のバッチ紐付けと元ファイル名 |
| `collectionMemberId` / `collectionScheduleId` | 集金取引から部員・集金設定へのドリルダウン |
| `createdBy` / `updatedBy` / `lastEditedAt` | 作業者の記録（単式運用での責任所在） |

これらが欠けると、**繰延・振替・集金の帳簿横連動が再現できない**。

## 6. データ量とストレージ見積り

### 6.1 1 クラブ・1 年あたり

| データ | 件数 | 算出根拠 |
|--------|------|---------|
| 取引 | 約 560 | 部費集金 30 人 × 12 ヶ月 = 360、その他収支 約 200 |
| 集金予定 | 360 | 30 人 × 12 ヶ月 |
| 集金実績 | 360 | 同上 |
| 予算行 | 150 | カテゴリ 5 × 科目 30 |
| 部員 | 30 | |
| 証憑 | 約 150 件 / 45 MB | 支出取引の一部。1 枚 300 KB 想定 |

### 6.2 規模別の合計

| 規模 | 年間レコード数 | DB 増加 / 年 | 証憑 / 年 |
|------|--------------|-------------|----------|
| 1 校（15 クラブ） | 約 20,000 | 約 40 MB | 約 675 MB |
| **20 校（初年度想定）** | **約 400,000** | **約 800 MB** | **約 13.5 GB** |
| 200 校（将来） | 約 4,000,000 | 約 8 GB | 約 135 GB |

**監査ログを加算する。** 1 レコードの変更ごとに `before` / `after` の JSONB を持つため、取引レコードの 2〜3 倍のサイズになる。20 校規模で **年間 約 1 GB**。

| 20 校規模の年間 DB 増加 | 約 1.8 GB（本体 0.8 + 監査ログ 1.0） |
|---|---|

**gp3 20 GB は 7〜10 年分に相当**し、初期容量として妥当。自動拡張の上限 100 GB に達するのは 200 校規模で 5〜8 年後。

**S3 証憑は 7 年保管で 20 校規模なら約 95 GB。** Glacier Instant Retrieval へ移行後の保管費用は月数百円規模で、設計書 §6.1 の見積り（月 300 円）に収まる。

## 7. タイムアウトと接続の仕様

### 7.1 一覧

| 箇所 | 値 | 設定場所 |
|------|-----|---------|
| ALB アイドルタイムアウト | **60 秒** | `ALB_IDLE_TIMEOUT_SEC` |
| コンテナ keep-alive | **65,000 ms** | `KEEP_ALIVE_TIMEOUT_MS` |
| ALB ヘルスチェック間隔 | 30 秒 / タイムアウト 5 秒 | `40-compute.sh` |
| ヘルスチェック閾値 | 正常 2 回 / 異常 2 回 | 同上 |
| ECS ヘルスチェック猶予 | 60 秒 | 起動直後の誤検知防止 |
| ターゲット登録解除待ち | 30 秒 | 既定 300 秒は 1 タスク運用には長すぎる |
| ECS `stopTimeout` | 30 秒 | |
| DB 接続のアイドルトランザクション | 60 秒 | `idle_in_transaction_session_timeout` |
| 深いヘルスチェックの DB 疎通 | 3 秒 | `/api/health/deep` |

### 7.2 ★ keep-alive の逆転は 502 を生む

**`KEEP_ALIVE_TIMEOUT_MS` は必ず `ALB_IDLE_TIMEOUT_SEC × 1000` より大きくすること。**

Node.js の `server.keepAliveTimeout` は既定 5 秒。ALB のアイドルタイムアウトは既定 60 秒。この状態だと、**ALB が「まだ生きている」と思って再利用しようとした接続を、Node 側が先に閉じている**という競合が起き、散発的な `502 Bad Gateway` が発生する。再現性が低く、原因究明に時間を取られる典型的な障害。

Next.js の standalone サーバー（`.next/standalone/server.js`）は **`KEEP_ALIVE_TIMEOUT` 環境変数（ミリ秒）を読んで `server.keepAliveTimeout` に設定する**実装になっている。これを使い、ALB より 5 秒長い 65,000 ms を指定する。

### 7.3 グレースフルシャットダウンの制約

standalone の `server.js` は `SIGTERM` を受けると **`process.exit(0)` で即座に終了する**（処理中のリクエストを待たない）。

したがって、デプロイ時に処理中のリクエストを守っているのは実質 **ALB のターゲット登録解除待ち（30 秒）だけ**である。ECS は先にターゲットグループから登録解除し、ドレイン完了後に `SIGTERM` を送るため、通常のリクエストは守られる。

ただし **30 秒を超える処理（大量 CSV の一括取込など）はデプロイ時に切られる可能性がある**。対策は 2 つ。

1. 長時間処理を作らない（CSV は分割取込、重い集計は SQL 側へ）
2. 必要になったら `NEXT_MANUAL_SIG_HANDLE=1` を設定し、自前の `SIGTERM` ハンドラでドレインする

現時点では 1 の方針とし、**デプロイは業務時間外に行う**運用ルールで補う。

## 8. アップロード仕様

現行実装には**サイズ制限が一切ない**（`accept="image/*"` / `accept=".csv"` のみ）。P4（証憑・ストレージ）で以下を実装する。

### 8.1 証憑画像

| 項目 | 値 |
|------|-----|
| 許可形式 | JPEG / PNG / HEIC / PDF |
| 1 ファイル上限 | **10 MB** |
| クライアント側の縮小 | 長辺 2000px・JPEG 品質 80 に再エンコードしてから送信 |
| 保存先 | S3（署名付き URL で直接 PUT。有効期限 5 分） |
| 閲覧 | 署名付き URL（GET、有効期限 15 分） |
| S3 キー | `{schoolId}/{clubId}/{fiscalYear}/{transactionId}/{uuid}.{ext}` |

**クライアント側で縮小する理由**: スマートフォンの写真は 3〜8 MB あり、そのまま保存すると 7 年分で容量が 10 倍近くなる。また 0.5 vCPU のサーバーで画像処理をすると他のリクエストを圧迫する。**縮小はブラウザ側で行い、サーバーは署名付き URL を発行するだけ**にする（Fargate を画像が通過しない）。

**OCR に渡すサイズ**: Gemini / Vertex AI への送信も縮小後の画像とする。現行は原寸の base64 を送っており、API 費用と応答時間の両方で不利。

### 8.2 CSV 取込

| 項目 | 値 |
|------|-----|
| 1 ファイル上限 | **5 MB** |
| 最大行数 | **5,000 行**（超過分はエラーで拒否し、分割を促す） |
| 文字コード（出力） | UTF-8 + BOM（Excel 対策。`src/utils/csvUtf8.ts`） |
| 文字コード（入力） | UTF-8 / UTF-8 BOM |

> **未対応**: 銀行が出力する CSV は **Shift_JIS のことが多い**が、現行実装は UTF-8 前提で BOM を除去するのみ（`stripLeadingCsvBom`）。Shift_JIS ファイルを読み込むと文字化けする。P3 の集金・取引移行時に、文字コード自動判別（`encoding-japanese` 等）の導入を検討する。**未決事項 Q-3。**

### 8.3 リクエストボディ上限

| 箇所 | 値 |
|------|-----|
| Next.js Route Handler | 既定（App Router に `bodyParser` 上限はないが、実装側で検証する） |
| 実装方針 | 画像は S3 へ直接 PUT するためサーバーを通らない。**JSON ボディは 1 MB を上限として検証する** |

## 9. 環境変数の契約

アプリが読む環境変数の一覧。**本番・ステージングでは `.env` を使わず、SSM Parameter Store から ECS タスク定義の `secrets` / `environment` で注入する。**

### 9.1 シークレット（SSM SecureString）

| 変数 | SSM パス | 用途 |
|------|---------|------|
| `DATABASE_URL` | `/kurasapo/{env}/DATABASE_URL` | PostgreSQL 接続文字列 |
| `AUTH_SECRET` | `/kurasapo/{env}/AUTH_SECRET` | Auth.js のセッション署名鍵（P1 で使用） |
| `GOOGLE_GEMINI_API_KEY` | `/kurasapo/{env}/GOOGLE_GEMINI_API_KEY` | 証憑 OCR |

**`DATABASE_URL` の形式**

```
postgresql://{user}:{pass}@{host}:5432/kurasapo?schema=public&connection_limit=5&sslmode=require
```

| パラメータ | 値 | 理由 |
|-----------|-----|------|
| `connection_limit` | `5` | §3.3。Prisma の既定（CPU 数依存）に任せない |
| `sslmode` | `require` | `rds.force_ssl=1` と対 |

### 9.2 非シークレット（タスク定義の `environment`）

| 変数 | 値 | 用途 |
|------|-----|------|
| `NODE_ENV` | `production` | |
| `PORT` | `3000` | 待受ポート |
| `HOSTNAME` | `0.0.0.0` | 全インターフェースで待受 |
| `TZ` | `UTC` | §2.2 |
| `KEEP_ALIVE_TIMEOUT` | `65000` | §7.2。ALB より長く |
| `NODE_OPTIONS` | `--max-old-space-size=640` | §3.1 |
| `APP_ENV` | `prod` / `staging` | 環境識別（ログ・Sentry のタグ） |
| `APP_REVISION` | イメージタグ | `deploy.sh` が埋め込む。`/api/health` が返す |
| `AWS_REGION` | `ap-northeast-1` | SDK 用 |
| `S3_RECEIPTS_BUCKET` | バケット名 | 証憑 |
| `S3_EXPORTS_BUCKET` | バケット名 | エクスポート |

### 9.3 ローカル開発

`.env.example` をコピーして `.env` を作る。`DATABASE_URL` の既定値は `docker compose up -d db` で起動する PostgreSQL を指す。

## 10. ログ仕様

### 10.1 形式

**構造化 JSON を 1 行 1 レコードで標準出力へ。** CloudWatch Logs が自動で取り込む。

| フィールド | 内容 |
|-----------|------|
| `level` | `debug` / `info` / `warn` / `error` |
| `time` | ISO 8601（UTC） |
| `msg` | メッセージ |
| `requestId` | リクエスト単位の相関 ID |
| `schoolId` / `clubId` | テナント識別。**学校からの問い合わせ時に該当校だけを追えるようにする** |
| `userId` / `role` | 操作者 |
| `path` / `method` / `status` / `durationMs` | HTTP |

保持期間は CloudWatch で 14 日（設計書 §6.1）。それ以上必要なものは監査ログ（DB）に残す。

### 10.2 ログに出してはならないもの

会計システムかつ個人情報を扱うため、以下は**マスクまたは出力禁止**とする。

| 項目 | 扱い |
|------|------|
| パスワード・ハッシュ・トークン | **絶対に出さない**（`DATABASE_URL` 全体を含む） |
| 部員・保護者の氏名 / メール / 電話 / 学籍番号 | **出さない**。必要なら ID のみ |
| 証憑画像の中身・base64 | 出さない |
| 取引金額 | エラー調査に必要な場合のみ `warn` 以上で。通常ログには出さない |
| 例外のスタックトレース | 出す（ただし上記を含まないこと） |

Sentry も同様に `beforeSend` でスクラビングする（設計書 §3.12）。
